1. Zakres mojego wkładu w projekt

W ramach projektu zespołowego Orthodontic Clinic App byłam odpowiedzialna za trzy główne obszary: moduł wizyt po stronie frontendu, moduł dokumentów binarnych pacjenta (backend i frontend) oraz konteneryzację aplikacji przy użyciu Docker. Poniżej opisuję każdy z tych obszarów szczegółowo.

Zrealizowane obszary: Moduł wizyt (frontend) Moduł dokumentów binarnych Backend PATCH /status Konteneryzacja Docker

2. Moduł wizyt

2.1. Widok kalendarza wizyt

Przygotowałam główny widok modułu wizyt — interaktywny kalendarz dostępny pod adresem /appointments. Komponent AppointmentCalendarView.vue obsługuje dwa tryby wyświetlania:

  • Widok miesięczny — siatka 7-kolumnowa (CSS Grid) obliczana przez właściwość computed calendarCells, uwzględniająca puste komórki na początku miesiąca, oznaczenie bieżącego dnia i przypisanie kolorów lekarzom z palety DOCTOR_PALETTE. Na każdej komórce dnia widać do 3 wizyt w postaci kolorowych pigułek oraz przycisk „+" otwierający formularz nowej wizyty z wypełnioną datą.
  • Widok tygodniowy — oś czasu 8:00–20:00, na której wizyty są pozycjonowane absolutnie względem slotów godzinowych. Kliknięcie pustego slotu otwiera formularz z wypełnioną datą i godziną.

Panel boczny wyświetla harmonogram wybranego dnia. Kliknięcie wizyty otwiera popup renderowany przez <Teleport to="body">, który umożliwia zmianę statusu i usunięcie wizyty bez opuszczania kalendarza.

2.2. Lista wizyt

Przygotowałam widok AppointmentListView.vue dostępny pod adresem /appointments/list. Widok oferuje:

  • klikalne filtry statusu z licznikami: Wszystkie / Zaplanowane / Potwierdzone / Zakończone / Anulowane / Nieobecność,
  • select filtrowania po lekarzu,
  • wyszukiwarkę tekstową po imieniu i nazwisku pacjenta, nazwisku lekarza i typie wizyty,
  • sortowanie malejące według daty,
  • modal potwierdzający usunięcie wizyty.

2.3. Formularze wizyt

Zaprojektowałam i zaimplementowałam formularze AppointmentAddView.vue i AppointmentEditView.vue z myślą o ergonomii klinicznej:

  • Karta daty — pole daty i godziny wyróżnione kartą z gradientem niebieskim; po wybraniu daty automatycznie wyświetla się czytelna etykieta słowna (np. „piątek, 6 czerwca 2026"),
  • Kafelki typów wizyty — zamiast selecta użytkownik klika jeden z 6 kafelków z ikoną emoji (🆕 Pierwsza konsultacja, 🔧 Kontrola aparatu, 🦷 Zakładanie aparatu, ✅ Zdjęcie aparatu, 📐 Retainer, 📌 Inne),
  • Pill-buttons statusu — kolorowe przyciski w kształcie pigułek zamiast selecta, z wizualnym wyróżnieniem wybranego statusu,
  • Prefilling z URL — formularz czyta parametry ?date, ?time, ?doctorId, ?patientId, dzięki czemu kliknięcie „+" na dniu kalendarza automatycznie wypełnia odpowiednie pola.

2.4. Typy i serwis wizyt

W pliku src/types/appointment.ts zdefiniowałam:

  • typ unii AppointmentStatus: 'Zaplanowana' | 'Potwierdzona' | 'Zakończona' | 'Anulowana' | 'Nieobecność',
  • stałe APPOINTMENT_STATUS_OPTIONS, APPOINTMENT_STATUSES, VISIT_TYPES,
  • interfejsy Appointment, AppointmentFormPayload, TimeSlot, VisitType,
  • funkcje pomocnicze formatAppointmentDate, emptyAppointmentForm, toAppointmentFormPayload.

W pliku src/services/appointmentService.ts dodałam funkcję updateAppointmentStatus(id, status) wysyłającą żądanie PATCH /api/Appointment/{id}/status.

3. Backend — endpoint PATCH /status

Rozszerzyłam istniejący AppointmentController o endpoint częściowej aktualizacji statusu wizyty, który jest wywoływany z popupu kalendarza i widoku szczegółów pacjenta:

[HttpPatch("{id}/status")]
public async Task<IActionResult> UpdateStatus(int id, [FromBody] UpdateStatusDto dto)
{
    try
    {
        var appointment = await _context.Appointments.FindAsync(id);
        if (appointment == null)
            return NotFound(new { message = "Wizyta nie istnieje." });

        appointment.Status = dto.Status;
        await _context.SaveChangesAsync();
        return Ok(new { message = "Status zaktualizowany.", status = dto.Status });
    }
    catch (Exception ex)
    {
        return StatusCode(500, new { message = "Błąd podczas aktualizacji statusu.", error = ex.Message });
    }
}

Endpoint przyjmuje tylko pole Status w ciele żądania, co pozwala uniknąć przesyłania całego obiektu wizyty przy prostej zmianie statusu.

4. Moduł dokumentów binarnych pacjenta

4.1. Model danych

Stworzyłam model PatientDocument przechowujący pliki binarne bezpośrednio w bazie danych SQL Server:

  • FileData — dane binarne pliku (byte[], mapowane na varbinary(max)),
  • FileName, ContentType, FileSize — metadane pliku,
  • Description — opcjonalny opis dodawany przez użytkownika,
  • UploadedAt — data przesłania,
  • PatientId — klucz obcy do tabeli Patients.

Dodałam DbSet<PatientDocument> PatientDocuments do AppDbContext i wygenerowałam migrację EF Core AddPatientDocuments.

4.2. Backend — PatientDocumentController

MetodaEndpointOpis
GET/api/PatientDocument/patient/{patientId}Lista dokumentów pacjenta — metadane bez danych binarnych
GET/api/PatientDocument/download/{id}Pobranie pliku binarnego jako FileContentResult
POST/api/PatientDocument/uploadPrzesłanie pliku multipart/form-data, maks. 10 MB
DELETE/api/PatientDocument/{id}Usunięcie dokumentu

Akcja Upload przyjmuje IFormFile, waliduje typ MIME (PDF, JPG, PNG, GIF, DOC, DOCX) i rozmiar (maks. 10 MB), odczytuje bajty przez MemoryStream i zapisuje je w bazie. Akcja Download zwraca File(byte[], contentType, fileName). W Program.cs skonfigurowałam limit rozmiaru żądania przez FormOptions i KestrelServerOptions.

4.3. Frontend — serwis i typy

W pliku src/types/document.ts zdefiniowałam interfejs PatientDocument oraz funkcje pomocnicze formatFileSize() i fileTypeIcon().

W pliku src/services/documentService.ts zaimplementowałam:

  • getPatientDocuments(patientId) — pobieranie listy dokumentów,
  • uploadDocument(patientId, file, description) — przesyłanie przez FormData,
  • downloadDocument(id, fileName) — pobieranie pliku z responseType: 'blob', tworzenie tymczasowego URL przez URL.createObjectURL i programatyczne kliknięcie <a download>,
  • deleteDocument(id) — usuwanie dokumentu.

4.4. Frontend — sekcja dokumentów w widoku pacjenta

Rozszerzyłam widok PatientDetailsView.vue o sekcję dokumentów zawierającą:

  • przycisk „Dodaj dokument" otwierający inline pasek uploadu z polem opisu i potwierdzeniem,
  • listę dokumentów z ikoną typu pliku, nazwą, rozmiarem, datą przesłania i opcjonalnym opisem,
  • przycisk pobierania (blob download) i usuwania z potwierdzeniem.

5. Konteneryzacja aplikacji (Docker)

Przygotowałam kompletną konfigurację Docker umożliwiającą uruchomienie całej aplikacji jednym poleceniem docker-compose up.

5.1. Dockerfile backendu

Plik backend/OrthodonticClinic.Api/Dockerfile używa wieloetapowego buildu:

  • etap build — obraz mcr.microsoft.com/dotnet/sdk:10.0, przywraca zależności NuGet i kompiluje projekt (dotnet publish),
  • etap final — lżejszy obraz mcr.microsoft.com/dotnet/aspnet:10.0, kopiuje skompilowane pliki i uruchamia aplikację.

5.2. Dockerfile frontendu

Plik frontend/Dockerfile też używa wieloetapowego buildu:

  • etap build — obraz node:22-alpine, instaluje zależności npm i buduje aplikację Vue (npm run build),
  • etap final — obraz nginx:alpine, kopiuje pliki statyczne z dist/ i uruchamia serwer Nginx.

5.3. Konfiguracja Nginx

Plik frontend/nginx.conf konfiguruje:

  • obsługę routingu SPA przez try_files $uri /index.html — dzięki temu odświeżenie strony na dowolnej ścieżce nie zwraca błędu 404,
  • proxy dla zapytań /api/ przekierowywane do serwisu backendowego w sieci Docker.

5.4. docker-compose.yml

Plik docker-compose.yml definiuje trzy serwisy:

SerwisObrazOpis
dbmcr.microsoft.com/mssql/server:2022-latestSQL Server 2022 z healthcheckiem
backendbudowany z DockerfileAPI .NET; uruchamia się po pozytywnym healthchecku bazy
frontendbudowany z DockerfileNginx serwujący SPA Vue, proxy /api/ do backendu

Serwisy komunikują się przez wewnętrzną sieć Docker. Zmienne środowiskowe connection stringa są przekazywane do backendu przez sekcję environment w pliku compose.

6. Napotkane problemy i poprawki

6.1. Błędny import komponentu w routerze

Przy podłączaniu modułu wizyt do routera aplikacji okazało się, że plik frontend/src/router/index.ts importował nieistniejący komponent AppointmentCalendarView.vue pod ścieżką /appointments, zamiast poprawnego AppointmentListView.vue. Błąd powodował awarię całej aplikacji przy próbie wejścia na zakładkę wizyt. Poprawiłam import i jednocześnie uzupełniłam brakujące trasy podstron modułu wizyt (/appointments/new, /appointments/:id, /appointments/:id/edit).

6.2. Niezgodność typów TypeScript w serwisie wizyt

Widok DashboardView.vue wywoływał funkcję getAvailableSlots z trzema argumentami i odwoływał się do właściwości .start na zwróconych elementach, podczas gdy serwis appointmentService.ts przyjmował tylko dwa argumenty i zwracał string[]. Podobny problem dotyczył funkcji getVisitTypes, która zwracała any[] zamiast typowanej tablicy. Naprawiłam obie funkcje — dodałam interfejsy TimeSlot { start: string } i VisitType { name: string } oraz opcjonalny trzeci parametr w getAvailableSlots, co wyeliminowało błędy kompilacji TypeScript.

7. Podsumowanie

W ramach projektu zrealizowałam samodzielnie trzy niezależne obszary funkcjonalne aplikacji:

  1. Moduł wizyt (frontend) — interaktywny kalendarz miesięczny i tygodniowy, lista wizyt z filtrami, formularze dodawania i edycji z nowatorskim interfejsem (kafelki typów, pill-buttons statusu, prefilling z URL), typy TypeScript i serwis komunikujący się z API.
  2. Moduł dokumentów binarnych — pełna obsługa przesyłania i pobierania plików binarnych: model danych z varbinary(max), migracja EF Core, kontroler REST z walidacją, serwis frontendowy z blob download, sekcja dokumentów w widoku pacjenta.
  3. Konteneryzacja Docker — wieloetapowe Dockerfile dla backendu (.NET) i frontendu (Vue + Nginx), konfiguracja Nginx z SPA fallback i proxy API, plik docker-compose.yml orkiestrujący trzy serwisy z healthcheckiem bazy danych.

Dodatkowo rozszerzyłam AppointmentController o endpoint PATCH /api/Appointment/{id}/status umożliwiający zmianę statusu wizyty bez przesyłania całego modelu, co jest wykorzystywane przez popup kalendarza.

W trakcie pracy natrafiłam na dwa błędy techniczne: niepoprawny import komponentu w routerze oraz niezgodność typów TypeScript w serwisie wizyt — oba zostały zdiagnozowane i naprawione (sekcja 6).
